## 1. 信息架构重构（已完成）

### 1.1 问题诊断

原 `projects.html` 把 109 张卡片一次性平铺，单页高度超过 4000px。三个具体毛病：

1. **无层级**——109 个项目同时呈现，无法「先看全局再看局部」
2. **无导航**——没有侧栏，滚动条是唯一的定位手段
3. **信息密度失衡**——每张卡片都展开四维信息，想找一个项目要先滚很久

### 1.2 新设计：入口树 + 逐级索引

```
┌────────────────┬──────────────────────────────────────┐
│  入口树（侧栏） │  内容区（逐级下钻）                    │
│                │                                       │
│  ▸ 总览        │  总览 › 具身智能 › ④ 示教 · 模仿学习   │  ← 面包屑
│  ▾ 具身智能 42 │  ─────────────────────────────────    │
│    ▸ ① RL地基  │                                       │
│    ▸ ④ 示教 6  │   [该层级的列表 / 详情]                │
│      · LeRobot │                                       │
│      · π0      │                                       │
│  ▸ AI Agent 67 │                                       │
│  ▸ 交叉地带 3  │                                       │
└────────────────┴──────────────────────────────────────┘
```

**四级下钻**，每级只呈现该级需要的信息：

| 层级 | 路由 | 呈现内容 | 信息量 |
|---|---|---|---|
| L0 总览 | `#/` | 统计 + 全景树图 + 3 个板块卡片 | 1 屏 |
| L1 板块 | `#/embodied` | 9 个分支卡片（含项目数/代码量/代表项目） | 1 屏 |
| L2 分支 | `#/embodied/3` | 该分支项目的**紧凑表格**（名称/仓库/说明/行数/star/架构状态） | 1 屏 |
| L3 项目 | `#/embodied/3/huggingface__lerobot` | 完整详情（语义架构 + 结构四维） | 可滚动 |

**关键设计决策**：

- **L2 用表格不用卡片**——分支内比较项目时，表格的对齐列比卡片更容易横向扫读
- **深链接可用**——每一层都有独立 URL，可直接分享「LeRobot 的架构分析」这个页面
- **侧栏树自动展开当前路径**并滚动到可见位置
- **语义架构标记**——侧栏里做过深度分析的项目带 `◆` 标记，一眼看出哪些是「精读过的」

### 1.3 验收标准

- [x] 4 个视图全部渲染无 `undefined` / `NaN` 泄漏
- [x] 路由解析正确（含深链接）
- [x] 侧栏树 139 个节点，当前路径高亮 + 自动滚动

### 2.1 优先级模型（满分 100）

**为什么需要排序**：109 个项目全部人工深读不现实。单项目高质量分析约需 15-30 分钟（读 README → 追调用链 → 定位扩展点），109 个就是 30-55 小时。必须按价值排序。

| 维度 | 权重 | 评分逻辑 | 理由 |

### 2.4 单项目产出规范（15 字段）

已固化为子 agent 的输出契约，见 `data/arch/*.json`：

```jsonc
{
  "repo": "huggingface/lerobot",
  "name": "LeRobot",
  "one_liner": "一句话说清它是什么（30 字内）",
  "problem": "它解决什么具体问题（80 字内）",
  "difficulty": "入门 | 中等 | 困难",
  "core_abstractions": [{"name": "", "role": "", "file": ""}],   // 7-10 个
  "layers": [{"name": "", "responsibility": "", "modules": [], "files": []}],  // 6-8 层
  "data_flow": ["第1步…", "…"],                                   // 10 步
  "entry_points": [{"path": "", "what": ""}],
  "key_files": [{"path": "", "why": ""}],                         // 8 个，按阅读顺序
  "extension_points": ["想扩展 X，改哪里"],
  "learning_path": ["第1步读什么", "…"],
  "diagram_mermaid": "graph TD\n  A[输入] --> B[处理]",
  "surprises": ["反直觉的设计"],
  "confidence": "高 | 中 | 低"
}
```

**为什么是这 15 个字段**：回答学习者的五个问题 —— ① 这是什么（one_liner/problem）② 系统怎么分层（layers）③ 数据怎么流（data_flow + diagram）④ 我该按什么顺序读（key_files + learning_path）⑤ 我要改的话从哪下手（extension_points）。

### 2.5 质量门禁

每个产出必须通过 `scripts/verify_arch.py`（待补）：

- [ ] 15 个字段齐全
- [ ] `diagram_mermaid` 以 `graph TD` 开头，**标签内无圆括号**（会破坏 Mermaid 解析）
- [ ] 所有 `file` / `path` 在本地仓库真实存在（防止幻觉路径）
- [ ] `confidence` 为「低」的项目需人工复核

## 3. 任务 B：网页工具改造

### 3.1 适用性模型（满分 100）

用户要求「除了优先级以外考虑适用性」。核心洞察：**一个包装后仍需要 GPU 才能用的工具，网页化价值大打折扣**——因为网页工具的意义是「打开就能用」，不是「换个地方跑训练」。

| 维度 | 权重 | 评分逻辑 |
|---|---|---|
| CLI 可包装 | 22 | 有 scripts 入口 +13 / 有命令名 +6 / 有 bin 字段 +3 |
| 算力门槛 | 20 | 无重依赖 20 / 仅需小模型 14 / 推理需 GPU 7 / 强 GPU 依赖 0 |
| 依赖轻量 | 18 | 核心依赖 ≤25 得满分；**探测不到依赖清单时给中位分 9**，不默认轻量 |
| 功能单一 | 15 | 5k-150k 行最佳（够用又不复杂） |
| 改造空间 | 10 | 已有 Web UI 得 0（重复造轮子） |
| 许可证 | 10 | MIT/Apache/BSD 满分；AGPL 3.5；GPL 5；**未标注 1.5**（公开分发有风险） |
| 活跃度 | 5 | 近 3 个月有推送满分 |

**两条硬门槛**（踩过的坑，已修正）：

1. **无 CLI 入口整体 ×0.45** —— 没有命令行入口的项目本质不是「命令行项目」，靠其他维度拿高分会产生误导。修正前 GR00T N1 和 A2A 协议都靠「依赖轻量 + 功能单一」拿到 80 分，但它们根本没有 CLI。
2. **规范仓 / 合集仓 / 基准仓 ×0.3** —— A2A 是协议规范仓，没有可包装的工具实体。

### 3.3 分层策略

按「能不能做出真正好用的东西」分三层，而不是一条线：

| 层 | 判定 | 项目示例 | 做法 |
|---|---|---|---|
| **A 类：直接可做** | 算力门槛 ≥14 且 CLI ≥13 | gpt-engineer · SWE-agent · Docling · markitdown · crawl4ai · ChatDev | 参数表单 + 实时输出 + 结果下载，一两天能出可用工具 |
| **B 类：需要 API Key 中转** | 算力门槛 ≥14 但依赖大模型 | MCP python-sdk · browser-use · TaskWeaver · smolagents | 后端不跑模型，走用户自带的 API Key |
| **C 类：暂不做** | 算力门槛 ≤7 | LeRobot · Genesis · LLaMA-Factory · smolagents | 训练/仿真类，网页化后仍要 GPU，性价比低 |

**优先做 A 类**。它们共同特征：输入明确（文件/URL/自然语言）→ 处理 → 输出明确（文件/报告），中间不需要 GPU。

### 3.4 改造范式

```
┌─────────────┐    ┌──────────────────┐    ┌─────────────┐
│  中文网页表单 │ →  │  FastAPI 后端     │ →  │  结果展示/下载 │
│  参数说明     │    │  调 CLI 子进程    │    │  进度流式推送  │
└─────────────┘    └──────────────────┘    └─────────────┘
```

三个必须解决的问题：

1. **参数翻译**——把 `--foo bar` 变成带中文说明的表单字段（可从 `--help` 自动提取）
2. **进度反馈**——CLI 是阻塞的，需要 `subprocess` + SSE 流式推送到前端
3. **错误翻译**——把英文 traceback 映射成中文可读提示

**注意许可证**：AGPL-3.0 项目（Firecrawl 等）改造成公开服务需开源衍生代码，私有使用则无此约束。

## 4. 子 agent 并行方案

### 4.1 结论：可以并行，且已实测

本次已用 3 个并行子 agent 完成第 1 批 9 个项目的语义分析，**约 8 分钟全部返回**（串行预估 25 分钟）。其中一个 agent 还自主发现 Isaac Lab 的克隆不完整并修复后完成分析。

### 4.2 为什么这个任务适合并行

| 特征 | 说明 |
|---|---|
| **可切分** | 项目之间零依赖，每个项目是独立分析单元 |
| **产出独立** | 每个项目写自己的 JSON 文件，无写入冲突 |
| **无需共享上下文** | 分析一个仓库只需该仓库的代码，不需要知道其他项目 |
| **验证成本低** | 产出是结构化 JSON，可程序化校验字段与路径真实性 |

### 4.3 并行策略

```
批次（8-10 个项目）
   │
   ├─ 子 agent 1  ── 3 个项目 ──┐
   ├─ 子 agent 2  ── 3 个项目 ──┤ 并发执行
   └─ 子 agent 3  ── 3 个项目 ──┘
                                 │
                        主 agent 汇总校验
                                 │
                        写入 data/arch/ 并重建看板
```

**切分原则**：按「主题相近」切，而不是按序号切。同一主题的项目放同一个 agent，它能读到相似的代码风格和术语，分析质量更高（第 1 批就是按「具身核心 / 具身基础设施 / Agent 核心」切的）。

**并发度**：3 个。上限取决于磁盘 I/O——每个 agent 都要遍历仓库读源码，并发过高会让 I/O 成为瓶颈（本次克隆时 4 并发就出现过连接挂死）。

### 4.4 质量控制（并行带来的风险与对策）

并行最大的风险是**质量不一致**——有的 agent 认真读代码，有的编造。三道防线：

1. **契约约束**——输出 schema 固定 15 字段，字段缺失直接判失败
2. **路径真实性校验**——所有 `file` / `path` 必须能在本地仓库找到，幻觉路径会被抓出
3. **置信度自评**——agent 必须标 `confidence`，标「低」的转人工复核

补充建议：**同一批里放 1 个项目做「对照」**，即主 agent 自己也分析一遍，与子 agent 结果比对，校准质量水位。

### 4.5 成本

| 项 | 单批（9 项目） | 全量（109 项目） |
|---|---|---|
| 子 agent 数 | 3 | 约 37 |
| 耗时 | 约 8 分钟 | 约 12 批 × 8 分钟 ≈ 1.6 小时（含评审） |
| 主要成本 | 每个 agent 读 10-30 万行代码的上下文 | 按批推进，可控 |

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 子 agent 编造架构 | 误导学习者 | 路径真实性校验 + 置信度标注 + 抽样人工复核 |

| 项目快速迭代导致分析过期 | 文档与代码不符 | 记录分析的 commit hash，标注「基于 xx 版本」 |
| 网页工具改造触碰许可证 | 法律风险 | 优先选 MIT/Apache；AGPL 项目仅私有使用 |
| 分析成本失控 | 投入产出比低 | 严格按批次推进，第 5 批（长尾）默认不做 |
